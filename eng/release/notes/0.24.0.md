# Runic editor extensions 0.24.0

Part of the Runic 0.24 release train: it belongs to
[Runic Command Line 0.15.0](https://github.com/Runic-Artifex/runic-cli-sdk/releases/tag/v0.15.0),
[Runic Translations 0.16.0](https://github.com/Runic-Artifex/runic-translations-sdk/releases/tag/v0.16.0)
and [Runic SDK 0.24.0](https://github.com/Runic-Artifex/runic-sdk/releases/tag/v0.24.0).
Runic DevKit now follows a Window project's frontend dependencies (client
libraries and JavaScript workspace packages), and F5 and Debug the Window
start the app with the arguments, launch profile and debugger options you
configured. Install Runic DevKit from the VS Code Marketplace or the Visual
Studio Marketplace, or a VSIX from this release (see Stores below).

| Asset | Extension | Version |
| --- | --- | --- |
| `runic-devkit.vsix` | VS Code, **Runic DevKit** (`runic-artifex.runic-devkit`) | `0.24.1000` |
| `runic-devkit-vs.vsix` | Visual Studio 2026, **Runic DevKit** (`RunicArtifex.DevKit.VisualStudio`) | `0.24.0.1000` |
| `SHA256SUMS` | `sha256sum` lines of both VSIX files | |

## Highlights

- **Frontend dependencies.** With runic-sdk 0.24's library packages, the Dev
  Session view (VS Code) and section (Visual Studio) list the packages the
  page imports, with their owner and state, and show a failed package build at
  its file. VS Code adds Build Frontend Dependencies, a click-to-install offer
  on a fresh clone and quick fixes for the dependency diagnostics. DevKit
  installs and builds nothing by itself (runic-editors#73, #74).
- **Only Window projects are `dev` targets.** Client libraries and test
  projects are no longer offered for `dotnet runic dev`, F5 or Debug the Window
  (runic-editors#73, #77).
- **The launch you configured.** VS Code's `runic` launch keeps `args`, `cwd`,
  `envFile`, the launch profile and every C# debugger option; Visual Studio's
  Debug the Window applies the active launch profile and passes the command
  line unsplit, so `/mock` in a profile reaches the Window (runic-editors#79,
  #80).
- **F5 says why `dev` stopped.** When `dev` exits early, F5 ends at once with
  `dev`'s own error, offers **Restore tools** on a fresh clone, and DevKit
  shows the failure from the session file however `dev` was started
  (runic-editors#81, #82, #85).
- **Ready for the Runic Artifex tool IDs.** Both extensions accept
  `RunicArtifex.Tool` (`dotnet rax`) and `rax-translations` next to
  `dotnet-runic` and `runic-translations` (runic-editors#72).

## Both extensions

- **Only Window projects are `dev` targets.** A project is a target of
  `dotnet runic dev` when it sets `RunicApplicationFrontendWindowProject`, or
  when it is an executable that is neither a client library nor a test
  project. Libraries and the template's test project are no longer offered for
  `dev`, F5, Debug the Window, Attach to the Page or (in VS Code) the `runic`
  tasks and doctor; before, `dev` failed on them with `RAPPDEV1005`. A folder
  or solution with only libraries shows "No Window project". The ViewModels
  and Doctor views still list every Runic SDK project (runic-editors#73, #78).
- **Frontend dependencies in the Dev Session.** A Window project's page can
  import other projects' frontend packages
  ([Library packages](https://github.com/Runic-Artifex/runic-sdk/blob/v0.24.0/packages/dotnet/Runic.Application.Views/README.md#library-packages),
  runic-sdk 0.24). The Dev Session lists them, dependencies first, with the
  owning project, the state (`built`, `building`, `failed` with `dev`'s
  message, `not built`, `source`, `build off`) and how `dev` keeps each
  current. While `dev` runs the rows come from the session file's
  `dependencies`; otherwise, and with an older `dev`, from the graph the last
  build wrote (`obj/runic/frontend-graph.json`). Opening a row opens its
  `package.json` (runic-editors#73, #74).
- **The Runic Artifex tool IDs.** Ahead of the rename in 0.25, both extensions
  accept `RunicArtifex.Tool` (`dotnet rax`) next to `dotnet-runic`, and
  `rax-translations` next to `runic-translations`, in `.config/dotnet-tools.json`
  or the root `dotnet-tools.json`; the new ID wins when a manifest lists both.
  They also follow a `dev` session under `obj/rax/`. An offer to run
  `rax migrate` appears only once `RunicArtifex.Tool` is available, so it
  doesn't show with 0.24. DevKit's own command, setting and store IDs don't
  change (runic-editors#72).

## VS Code

- **Frontend dependency commands, behind a click.** **Build Frontend
  Dependencies (dotnet build)** builds the Window project, whose Views targets
  install the JavaScript workspace and build each package. On a fresh clone
  without `node_modules`, a status bar item and a view row offer **Install
  Frontend Dependencies**, the locked install the targets run
  (`bun install --frozen-lockfile --ignore-scripts`,
  `pnpm install --frozen-lockfile --ignore-scripts` or `npm ci --ignore-scripts`),
  after you confirm it. Quick fixes cover `RUNICBRIDGE026`, `087`, `088`, `089`
  and `090` and `RAPPDEV1018` (runic-editors#73).
- **The `runic` launch keeps your configuration.** A `runic` configuration's
  `args` reached the C# debugger as `[]`. It now passes MSBuild's
  `RunArguments`, then the launch profile's `commandLineArgs`, then `args`; the
  profile's `environmentVariables`, `envFile` and `env` (the session's Runic
  variables last); `cwd`, else the profile's `workingDirectory`; and every C#
  debugger option (`console`, `stopAtEntry`, `justMyCode`, …) unchanged. The
  launch profile is the first `Project` profile of
  `Properties/launchSettings.json`, or the one `launchProfile` names; a missing
  named profile stops F5 with an error. `devArgs` passes options to the
  `dev --no-window` that F5 starts. Arguments with quotes, such as
  `/config:"C:\Program Files\Acme\dev.json"`, are split as .NET splits them.
  Run and Debug offers one entry per Window project and launch profile, named
  "Runic: Acme.App (Mock data)" instead of "Runic: Window" (runic-editors#80).
- **Any `coreclr` debugger.** The C# extension check accepts any installed
  extension that contributes a `coreclr` debugger. The launch log no longer
  prints variable values (runic-editors#80).
- **F5 stops at once when `dotnet runic dev` exits early.** When the `dev` that
  F5 starts exits before its session is ready, F5 ends with `dev`'s exit code and
  last output lines, instead of showing "starting dotnet runic dev" until its
  10-minute timeout.
- **Restore tools, behind a click.** On a fresh clone whose local tools aren't
  restored, F5's error (and a `dev` started from the Dev Session view) offers
  **Restore tools**, which runs `dotnet tool restore` as a task; press F5 again
  afterwards. DevKit restores nothing by itself.
- **Restart rebuilds.** Restart (Ctrl+Shift+F5) of a `runic` session started
  the Window from the old build: VS Code restarts the resolved `coreclr`
  configuration without DevKit. DevKit's build is now that configuration's
  `preLaunchTask`, so Restart builds again, with the same arguments and the same
  `dev`. A build with errors stops the launch as `debug.onTaskErrors` says.
- **A library's TypeScript error appears once in Problems.** When a frontend
  package's build failed (`RAPPDEV1018`), Problems listed its error three times:
  in the package's file, under the sentence of `dev`'s message as if it were a
  file, and in a `src/index.ts` of the Window project that doesn't exist. It now
  lists it in the package's file, beside `RAPPDEV1018` on the project. A watcher's
  relative error line (`[shared-ui] src/x.ts(3,1): …`) goes to that package's file.
- **The dependency tree shows a failed package build.** After `dev` stopped on a
  package's build error, the Dev Session view still said "built" from an earlier
  build's files. It now says "failed" with the error, as Problems does, until the
  next `dev`.
- **However `dev` was started.** VS Code removes a background task's problems
  when its process ends, so a `dev` that stopped at its start left Problems empty
  and the package "built" when VS Code ran the runic-app template's `runic: dev`
  task (F5's `preLaunchTask`, Terminal > Run Task). With runic-sdk 0.24, `dev`
  writes its failure into the session file, and DevKit now shows those errors in
  Problems and the package "failed" in the tree after the task has ended,
  whichever way `dev` was started, each error once, until the next `dev` starts.
  An older `dev`, whose session file has no failure, works as before.
  On a project that has never been built, which has no frontend graph yet, the
  tree now shows the failed package too, by its package.json name (else its
  folder) and owning project, with its errors below it; after a build the
  graph's row takes over.
- **No "no registered task type" lines.** The Restore tools task and the
  package-manager tasks of the quick fixes used task types that the extension
  didn't declare, which VS Code's Tasks output reported.
- **Each Run and Debug entry once.** The dynamic "Runic Window…" list showed every
  Window project and profile twice, under its folder and again under "user
  settings". It now lists each once, under its folder.

## VS Code and Visual Studio

- **Launch profile values must be strings in both.** VS Code's reader dropped a
  number such as `"PORT": 8080` without a word; it now refuses the file with the
  same message as Visual Studio.

## Visual Studio

- **Debug the Window applies the active launch profile.** It ignored the
  launch profile, so a `/mock` set there never reached the Window. It now
  passes the project's `RunArguments`, then the active `Project` profile's
  `commandLineArgs`, as one command line that is never split and quoted again
  (so `/config:"C:\Program Files\x"` arrives intact), with the profile's
  `environmentVariables` and `workingDirectory`. The active profile is the one
  the toolbar shows, else the first, as Visual Studio's own F5 picks it
  (runic-editors#79).
- **F5 stops with `dev`'s own error, and offers to restore the tools.** When the
  `dev --no-window` that F5's Yes started exits before it is ready, the message
  shows `dev`'s exit code and last output lines instead of pointing to an empty
  Error List. On a fresh clone whose local tools aren't restored, it asks whether
  to run `dotnet tool restore` (the same for Debug the Window and Start dotnet
  runic dev); press F5 again afterwards. DevKit restores nothing by itself.
- **Debug the Window no longer waits for a page that can't come.** A Window
  outside Development (a launch profile with `DOTNET_ENVIRONMENT=Staging`) opens
  no page endpoint. Debug the Window now says so at once and stops waiting after
  20 seconds, naming the variable and its value. Time Visual Studio spends in a
  dialog (the Release "Just My Code" warning) no longer counts toward the
  three-minute wait for a page.
- **Launch profiles that Visual Studio refuses.** A profile variable,
  `commandLineArgs` or `workingDirectory` that isn't a string (`"PORT": 5000`)
  makes Visual Studio's own F5 refuse the file, while Debug the Window accepted
  it. It now refuses the file too and says how to write the value.
- **Message boxes in front.** DevKit's messages (such as Attach to the Page's)
  no longer open behind the app's Window, where they blocked Visual Studio.
- "is an Executable profile" instead of "is a Executable profile".

## Runic Translations

Both extensions are tested with `dotnet-runic-translations` 0.16.0 from NuGet
(the repository's tool manifest). Its language server still speaks protocol 2,
and it reads a package's library catalog in the renamed format too; DevKit
needs no change for that. Workspaces on Translations 0.15.1 keep working. The
bundled `runic.json` schema is unchanged. Use the version of the project's
`Runic.Translations` packages:

```sh
dotnet tool install dotnet-runic-translations --version 0.16.0
```

## Verifying

```sh
sha256sum --check SHA256SUMS
gh attestation verify runic-devkit.vsix -R Runic-Artifex/runic-editors \
  --signer-workflow Runic-Artifex/runic-editors/.github/workflows/release.yml
gh attestation verify runic-devkit-vs.vsix -R Runic-Artifex/runic-editors \
  --signer-workflow Runic-Artifex/runic-editors/.github/workflows/release.yml
```

The release workflow takes both VSIX files from the successful CI run of the
released commit and checks them by hash before attesting them. From this
release, PR CI and the release's dry run also run both stores' own offline
upload checks (vsce's and VsixPublisher's), so a VSIX a store would refuse
fails before anything is published (runic-editors#70).

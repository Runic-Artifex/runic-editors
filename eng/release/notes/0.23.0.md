Part of the Runic 0.23 release train: it belongs to
[Runic Translations 0.15.1](https://github.com/Runic-Artifex/runic-translations-sdk/releases/tag/v0.15.1)

## No Preview label

Runic Translations 0.15 completes the language server's production work
(large-catalog budgets in CI, a compatibility promise for its standard surface
and the `runic` protocol), so both extensions are published without the
Marketplace "Preview" label (runic-editors#50). Before 1.0, a minor release can
still change commands and settings; the release notes list every change.

## Both extensions

- **Frontend errors as problems.** With `dotnet-runic` 0.23, `dotnet runic dev`
  prints each Vite error as an MSBuild-form `RUNICP008` line and a clear line
  once the modules compile again. Both extensions show these errors as problems
  (the Error List in Visual Studio, Problems in VS Code) at their file and line,
  and remove them at the clear line. A successful .NET build no longer removes a
  `.tsx` error. `RUNICP` codes link to runic-sdk's diagnostics reference
  (runic-editors#52).
- **The forced stop reaches `dev`.** When `dotnet runic dev` doesn't stop on its
  input within 10 seconds, it is ended by force. Off Windows, VS Code now signals
  the whole process group of the `dotnet` launcher, so `dev`, its frontend
  server and its Window end too; before, only the launcher was killed
  (runic-editors#53). On Windows, Visual Studio's job now also holds processes
  `dev` started before the job was assigned, and `taskkill /T` runs before the
  job is ended, so none of them is left running (runic-editors#58).

## Visual Studio

- **Visual Studio closes while a page attach is stuck.** Debug the Window and
  Attach to the Page now start the JavaScript debugger with a js-debug attach
  configuration (`IVsDebugger4.LaunchDebugTargets4`), which returns at once,
  instead of `Process2.Attach2`, whose nested wait kept Visual Studio from
  closing when the attach never completed. If the attach doesn't complete within
  60 seconds, or Visual Studio starts closing, DevKit ends the waiting adapter.
  JavaScript adapters left over from an earlier Visual Studio are ended before
  an attach (runic-editors#44).
- **Break All in Debug the Window stops only the .NET Window.** While Debug the
  Window debugs a WebView2 Window and its page, **Debug → Break All** breaks the
  Window's .NET process alone. The page keeps running and its breakpoints still
  stop it. Visual Studio no longer repeats "The script document cannot be
  opened" (runic-editors#43).
- **The page attach uses 127.0.0.1 and checks the port's owner.** The attach
  never falls back to `localhost`, which can resolve to `[::1]`. Before it
  attaches, DevKit checks that the DevTools port belongs to the Window, a
  process the Window started, or a process of yours started after the Window.
  When another program holds the port (such as CS-WebUI's fixed 9225), the
  attach stops and names that program. Attach to the Page no longer offers an
  endpoint that the dev session lists as unavailable.
- **The language server asks before it starts outside the solution.** A tool
  manifest in the open solution's folder starts the Translations language
  server as before. For a manifest anywhere else (above the solution, or for a
  document opened without a solution), DevKit first asks whether you trust that
  folder, because `dotnet` uses its `global.json`, NuGet configuration and tool
  manifest. A Yes is remembered for the folder. After a No, **Tools → Runic →
  Restart Language Server** asks again. VS Code already runs only in trusted
  workspaces.
- **Known limits** name the remaining case of the WebView2 spike
  (runic-sdk#1192). A C# breakpoint hit while the page has the focus makes the
  page's DevTools endpoint and input wait until Continue. Visual Studio doesn't
  hang.

## Runic Translations

Both extensions are tested with `dotnet-runic-translations` 0.15.1 from NuGet
(the repository's tool manifest), which fixes a flaw in 0.15.0's pack loading
([GHSA-24g5-pcc5-4fg7](https://github.com/Runic-Artifex/runic-translations-sdk/security/advisories/GHSA-24g5-pcc5-4fg7)).
The 0.15 language server speaks only protocol 2,
which Runic DevKit has asked for since 0.22, so runic-editors 0.21 and earlier
can't use it. Workspaces on Translations 0.14.0 keep working. The bundled
`runic.json` schema is unchanged. Use the version of the project's
`Runic.Translations` packages:

```sh
dotnet tool install dotnet-runic-translations --version 0.15.1
```

## Stores

Runic DevKit for VS Code is on the VS Code Marketplace as
[runic-artifex.runic-devkit](https://marketplace.visualstudio.com/items?itemName=runic-artifex.runic-devkit)
(`0.23.1000`). Runic DevKit for Visual Studio is on the Visual Studio Marketplace
as [runic-artifex.runic-devkit-vs](https://marketplace.visualstudio.com/items?itemName=runic-artifex.runic-devkit-vs)
(`0.23.0.1000`), which gets final versions only. Both are published from this
release's VSIX files by trusted publishing. Runic DevKit isn't on Open VSX: in
VSCodium, Cursor or Windsurf, install `runic-devkit.vsix` from this release.

## Verifying

```sh
sha256sum --check SHA256SUMS
gh attestation verify runic-devkit.vsix -R Runic-Artifex/runic-editors \
  --signer-workflow Runic-Artifex/runic-editors/.github/workflows/release.yml
gh attestation verify runic-devkit-vs.vsix -R Runic-Artifex/runic-editors \
  --signer-workflow Runic-Artifex/runic-editors/.github/workflows/release.yml
```

The release workflow takes both VSIX files from the successful CI run of the
released commit and checks them by hash before attesting them. A store-only
dispatch now publishes the files of an existing GitHub release after checking
their hashes and attestations.

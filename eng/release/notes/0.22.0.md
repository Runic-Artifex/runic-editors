# Runic editor extensions 0.22.0

Part of the Runic 0.22 release train: it belongs to
[Runic Translations 0.14.0](https://github.com/Runic-Artifex/runic-translations-sdk/releases/tag/v0.14.0)
and [Runic SDK 0.22.0](https://github.com/Runic-Artifex/runic-sdk/releases/tag/v0.22.0).
Runic DevKit for Visual Studio reaches parity with VS Code in this release. Install
Runic DevKit from the VS Code Marketplace or the Visual Studio Marketplace, or a
VSIX from this release (see Stores below).

| Asset | Extension | Version |
| --- | --- | --- |
| `runic-devkit.vsix` | VS Code, **Runic DevKit** (`runic-artifex.runic-devkit`) | `0.22.1000` |
| `runic-devkit-vs.vsix` | Visual Studio 2026, **Runic DevKit** (`RunicArtifex.DevKit.VisualStudio`) | `0.22.0.1000` |
| `SHA256SUMS` | `sha256sum` lines of both VSIX files | |

## Both extensions are Runic DevKit

Both extensions are now named **Runic DevKit** and have new identities, the ones
they will keep on the VS Code Marketplace and the Visual Studio Marketplace
(D070.5):

| Editor | Until 0.21 | Since 0.22 |
| --- | --- | --- |
| VS Code | **Runic**, `runic-artifex.runic`, `runic.vsix` | **Runic DevKit**, `runic-artifex.runic-devkit`, `runic-devkit.vsix` |
| Visual Studio 2026 | **Runic MF2 Translations**, `Runic.Artifex.Translations.Rmf2`, `runic-translations-visualstudio.vsix` | **Runic DevKit**, `RunicArtifex.DevKit.VisualStudio`, `runic-devkit-vs.vsix` |

Command IDs (`runic.*`), settings, views and command titles are unchanged. Each
editor installs Runic DevKit next to the former extension, so **uninstall the
former one**: while both are installed, both register the same commands and start
a language server for the same files.

- **VS Code:** on activation Runic DevKit finds Runic (`runic-artifex.runic`) and
  the older Runic MF2 Translations (`runic-artifex.runic-translations`) and offers,
  in one notification, to uninstall them; then reload the window. See [Moving from
  Runic or Runic MF2 Translations](https://github.com/Runic-Artifex/runic-editors/blob/v0.22.0/vscode/README.md#moving-from-runic-or-runic-mf2-translations).
- **Visual Studio:** when a solution is open, Runic DevKit finds Runic MF2
  Translations through the extension manager and shows an InfoBar: **Extensions >
  Manage Extensions > Installed**, select **Runic MF2 Translations**, **Uninstall**,
  restart. Keyboard shortcuts assigned to the former Tools-menu commands need to
  be assigned again. See [Moving from Runic MF2
  Translations](https://github.com/Runic-Artifex/runic-editors/blob/v0.22.0/visualstudio/README.md#moving-from-runic-mf2-translations).

## VS Code

With Translations 0.14, the Translations refactorings use F2 and the light bulb:
F2 renames inputs (`$name`) and slot references (`ref=`) as well as resources and
MF2 locals, and the light bulb offers **Extract group** on a group's name and
**Inline into ../en.rmf2** in a feature-local resource. The palette commands
remain and open the same rename box or code action; with Translations 0.13 they
work as in 0.21. A resource rename in a workspace with application sources asks
first (**Rename in resource sources** or **Cancel**). When the server rejects a
light-bulb refactoring as outdated (files changed between the code action and
its resolve, such as a save's file-watcher event), the extension resolves it
once more and, if it is still outdated, shows a warning instead of applying
nothing (runic-editors#32). In a multi-root workspace, each folder's language server now
starts even when several folders hold Translations projects.

With `dotnet-runic` 0.22, the extension's `dev` task passes `--debug-endpoint` to
a `dev` with its Window, so a CS-WebUI Window opens its DevTools Protocol port
(D070.17), and **Stop dotnet runic dev** asks `dev` to stop on its standard input
(`RUNIC_DEV_STOP_ON_INPUT`), so it marks its session stopped and removes its
development pages, on Windows too; after 10 seconds it is ended by force. Older
tools run as in 0.21.

When a `dev` was killed (the session file still says starting or ready, but its
process is gone), the extension now touches `obj/runic/dev-stopped` once, as
`dev` does when it stops, so the next build restores the production frontend in
`www/` (runic-editors#29).

A light-bulb refactoring the server refuses for another reason (such as Extract
Group while a locale lacks the group) shows the server's reason as a warning,
and the palette's Extract Group and Inline Resource work right after a save:
the extension asks again for a few seconds when the server answers that the
document changed while the request was pending. `dotnet runic dev`'s build
errors open their file again (the `$runic-dev` matchers skip `dev`'s `[host] `
label), and with `dotnet-runic` 0.22 a fixed C# error leaves Problems once `dev`
prints `[dev] Ready` again, while warnings stay (runic-editors#36, #38, #40).

## Visual Studio

The Visual Studio commands move to a **Tools → Runic** submenu (their command
names `Tools.RunicPreviewMessage` and `Tools.RunicRestartLanguageServer` stay), and
**Preview Message** is also in the `.mf2`/`.rmf2` editor context menu.
**View → Other Windows → Runic** opens the new Runic tool window.

**Tools → Options → Runic DevKit** sets the .NET executable, the language server
assembly and the language server trace (VS Code's `runic.dotnetPath`,
`runic.translations.serverAssembly` and `runic.translations.trace.server`); the
`RUNIC_DOTNET` and `RUNIC_TRANSLATIONS_SERVER` environment variables still apply
while an option is empty. The language server's output and trace go to a
**Runic Translations** Output pane (the Runic SDK commands write to a **Runic SDK** pane). When the server cannot start, an InfoBar says why once per solution
(no tool manifest, tool not restored, missing .NET runtime, a tool without `lsp`),
with **Show output** and **How to install the tool**. Runic DevKit now loads only
in a solution with a Runic project (the `RunicApplication` capability, a Runic
Translations build, a `runic.json` or a tool manifest with
`dotnet-runic-translations`) or when an `.mf2`/`.rmf2` file is open, and the
**Tools → Runic** menu shows only there.

The Runic tool window shows, for the solution's Runic SDK projects, the
**ViewModels** of the development source map (`runic-bridge/sources.json`) with
their Bridge members; double-click a member, or choose **Open C# Member**, to go
to its C# source. **Run dotnet runic doctor** (Tools → Runic, the tool window's
toolbar, the Error List's context menu) shows the checks in the **Doctor**
section and puts failing and warning checks into the Error List on the project
file, with a help link (F1) to the doctor documentation, as VS Code's Doctor view
and Problems do.

**Start dotnet runic dev**, **Start dotnet runic dev --no-window** and **Stop
dotnet runic dev** (Tools → Runic, the tool window's toolbar) run `dev` as VS
Code's tasks do: its output goes to the **Runic SDK** Output pane and its
diagnostics, read as VS Code's `$runic-dev` problem matcher reads them, to the
Error List with a help link (F1) for Runic codes. The extension follows each
project's `obj/runic/dev-session.json` and checks that its `dev` still runs by
process ID and start time. A `dev` started in a terminal is followed but stopped
there with Ctrl+C. **Open the Development Server** and **Open the dev Session
File** open the session's server and file. When F5 or Ctrl+F5 starts a Runic
startup project and no `dev --no-window` runs for it, Visual Studio asks first:
start `dev --no-window` and launch once it is ready, or continue without it
(D070.6). The doctor and `dev` use the **.NET executable** option, and the doctor's
output now goes to the Runic SDK pane.

The tool window's **Dev Session** section shows each project's `dev` state and,
while it runs, the development server, the Window's owner or process, the pages,
the debug endpoints and the generated clients, as VS Code's Dev Session view does.
The toolbar enables Start and Stop by state, and state changes appear in the
status bar.

**Debug the Window** (Tools → Runic, the tool window's toolbar) debugs the .NET
code and the page in one session: it starts `dev --no-window`, builds, launches
the Window under the .NET debugger with the session file's environment and a
DevTools Protocol port (a free one in `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` for
WebView2, the session's for CS-WebUI), and attaches the JavaScript debugger over
CDP once the page is up, with no 30-second limit. **Attach to the Page
(JavaScript)** attaches to a running page from the session file's
`debugEndpoints`. When DevKit starts `dev` with its Window, it passes
`--debug-endpoint` to `dotnet-runic` 0.22 and later, so CS-WebUI Windows open
their port. TSX breakpoints need runic-sdk 0.22's `vite-plugin-runic`; this
replaces the template's `(WebView2 script debugging)` profile, which does not
work in Visual Studio.

With `dotnet-runic` 0.22, **Stop dotnet runic dev** asks `dev` to stop on its
standard input instead of ending its process tree, so the session file says
stopped and the development pages leave `www/`; after 10 seconds it ends the tree
as before. **Debug the Window** no longer stays disabled after a hung JavaScript
attach or a `.vs` reset: DevKit stops waiting for an attach after 60 seconds, says
so in the Runic SDK Output pane, and reopening the solution ends a waiting run
(runic-editors#23). The README's troubleshooting now says to delete `.vs` when
Visual Studio's JavaScript debugger fails to attach.

When a `dev` was killed (`taskkill /F`, a crash, Visual Studio ending its task),
DevKit touches its project's `obj/runic/dev-stopped` once, as `dev` does on a
clean stop, so the fast up-to-date check lets the next F5 build and put the
production frontend back in `www/` instead of running with `dev`'s development
page (runic-editors#29, runic-sdk#1121).

With Translations 0.14, the Translations refactorings come to Visual Studio
through F2 and the light bulb (DevKit requests the language server's protocol
2): F2 renames inputs (`$name`) and slot references (`ref=`, with their
`runic.json` contracts) as well as resources and MF2 locals; a resource rename
in a solution with application sources asks in an InfoBar (**Rename in resource
sources** or **Cancel**); the light bulb offers **Extract group** on a group's
name and **Inline into ../en.rmf2 (leaves en.rmf2 empty)** in a feature-local
resource. Visual Studio cannot delete files through LSP, so Inline empties the
child file; once that file and the ancestor are saved, DevKit deletes it
through its project item (Solution Explorer and source control follow) and
says so in the Runic Translations pane. Only the emptied file is deleted, and
only while it is saved and empty: undo the Inline or write into the file and it
stays. The server watches the solution's Runic files itself, as Visual Studio
cannot register watchers for it. When the server refuses a rename (an invalid
name, a catalog that does not compile), Visual Studio closes the rename box
without a message; DevKit now shows the server's reason in an InfoBar, the
status bar and the Runic Translations Output pane (runic-editors#32).
Visual Studio does not create the folder of a new file, so **Extract group** into
a folder that does not exist yet (such as `counter/en.rmf2`) would keep only the
removal from the source: DevKit creates the folder first, only inside the
solution or the Translations project, and notes it in the Runic Translations
pane; if it cannot, Visual Studio applies none of the edit and an InfoBar says
why (runic-editors#38). Visual Studio's LSP client saves an F2 rename at once:
it writes every renamed file to disk, open documents included.

In a solution with only Runic Translations, the Runic SDK commands and
the Dev Session, ViewModels and Doctor sections stay hidden until a Runic SDK
project is found. Selected tool-window rows use the theme's tree selection
colours, and the sections are no longer extra Tab stops. `dev`'s C# and
`RUNICBRIDGE` build errors in the Error List open their file, and a fixed one
leaves the Error List once `dev` reports `[dev] Ready` again. Frontend (`.tsx`)
errors from Vite stay in the Runic SDK Output pane and the page's error overlay
(runic-editors#35).

The Translations tools of VS Code come to **Tools → Runic**: **Export XLIFF…**,
**Import XLIFF (Dry Run)…** and **Import .resx or i18next Catalog…** (a dry run,
then the import after confirmation) run the project's local `runic-translations`
tool with file and folder pickers and write its output to the Runic Translations
Output pane. **Override Library Message…** (also in the editor context menu)
picks an installed library catalog, message and locale and opens the override
source `runic-translations overrides add` writes. Go to Definition in an override
source opens the library's source read-only. The tool window's **Translations**
section shows each locale's coverage from `runic-translations status`, with
**Show Translation Status** (a read-only report) and **Refresh Translation Status**.

## Runic Translations

Both extensions are tested with `dotnet-runic-translations` 0.14.0 from NuGet
(the repository's tool manifest), whose language server protocol 2 they
request; the bundled `runic.json` schema is unchanged. Workspaces on
Translations 0.13.0 keep working without the protocol 2 refactorings. Use the
version of the project's `Runic.Translations` packages:

```sh
dotnet tool install dotnet-runic-translations --version 0.14.0
```

## Stores

Runic DevKit for VS Code is on the VS Code Marketplace as
[runic-artifex.runic-devkit](https://marketplace.visualstudio.com/items?itemName=runic-artifex.runic-devkit)
(`0.22.1000`, with the Preview label), published from this release's VSIX by trusted

[runic-artifex.runic-devkit-vs](https://marketplace.visualstudio.com/items?itemName=runic-artifex.runic-devkit-vs)
(`0.22.0.1000`, with the Preview label), published the same way; that store gets
final versions only, so release candidates stay on the GitHub releases. Both
Marketplace listings are new with this release. Runic DevKit is not on Open VSX
for now: in VSCodium, Cursor or Windsurf, install `runic-devkit.vsix` from this
release.

## Verifying

```sh
sha256sum --check SHA256SUMS
gh attestation verify runic-devkit.vsix -R Runic-Artifex/runic-editors \
  --signer-workflow Runic-Artifex/runic-editors/.github/workflows/release.yml
gh attestation verify runic-devkit-vs.vsix -R Runic-Artifex/runic-editors \
  --signer-workflow Runic-Artifex/runic-editors/.github/workflows/release.yml
```

The release workflow takes both VSIX files from the successful CI run of the
released commit and checks them by hash before attesting them.
